# 1. 背景与问题定义

CommerceCanvas 当前 G2 前端已经建立：

- Graphite Canvas 深色工作台视觉；
- AppShell；
- Competitor Analysis；
- Live Intelligence；
- Evidence / Trace；
- Job Detail；
- Persistent Task；
- 跨路由状态持续；
- 六区域任务详情结构。

这些已经解决了“产品像不像一个工作台”的第一层问题。

当前仍明显不足的是第二层：

> **工业软件级 UI grammar、文字层级、视觉密度、交互状态和组件一致性。**

主要表现包括：

- 字体尺寸、字重和 line-height 缺少严格层级；
- Page / Section / Panel / Label / Metadata 之间视觉权重不稳定；
- `12px / 13px / 14px` 等字号容易按页面局部需求随意出现；
- Row 高度、padding、gap、icon alignment 不统一；
- Badge 使用范围过宽；
- Card 套 Card；
- 部分信息更适合 Row / Table / List，却被做成 Card；
- hover / pressed / focus / disabled / loading 状态不统一；
- Tooltip / Popover / Dialog / Menu 等细节仍有 prototype 感；
- 状态色容易由单个组件自行决定；
- 中文长文本、ID、时间、成本、模型名、状态之间缺乏系统化排版规范；
- 新页面如果继续自由开发，会进一步扩大视觉债务。

G2-F3.5 的目标不是“重新设计 CommerceCanvas”，而是：

> **保留 Graphite Canvas 产品语言，用 Astryx 的工业级设计系统能力建立稳定的底层 UI grammar。**

# 3. 关键兼容性事实：React 19 是第一道门禁

截至本计划编写时，Astryx 官方明确要求：

```text
React 19+
react-dom 19+
```

而 CommerceCanvas 当前前端基线为：

```text
React 18
TypeScript strict
Vite 5
Tailwind 3
Lucide
```

因此：

> **F3.5 绝对不能直接安装 Astryx 然后开始换组件。**

必须先进行 React 18 → React 19 Compatibility Gate。

---

## 5.2 禁止 Astryx CLI 覆盖治理文件

Astryx CLI 的 `init` 会向：

```text
AGENTS.md
CLAUDE.md
```

写入 Agent component guidance。

CommerceCanvas 已有自己的 Implementer 治理和 `execution-discipline`。

因此：

> **禁止直接运行会无审查覆盖 / 修改治理文件的初始化流程。**

如果需要 `astryx init`：

1. 先备份 / diff；
2. 先确认具体会修改哪些文件；
3. 不允许覆盖 `.zcode/AGENTS.md` 的治理语义；
4. Astryx component index 应作为 UI reference，而不是治理替代；
5. 必须由 Reviewer 检查 diff。

如 CLI 支持只读 docs/component 查询，优先采用只读方式。

---

## 5.3 Tailwind 3 共存

CommerceCanvas 当前使用 Tailwind 3。

Astryx 官方支持 Tailwind v3 渐进共存，但 CSS cascade layer 必须显式控制。

F3.5 必须：

- 审计当前 global CSS；
- 审计 Tailwind preflight；
- 审计现有 reset；
- 建立明确 cascade layer；
- 保证 Astryx component base/theme 不被 legacy reset 静默覆盖；
- 保留 Tailwind utilities 作为迁移期间 legacy layout 工具；
- 禁止同一语义同时存在多套长期 token。

## 6.3 Token Source Rule

组件不得自行长期保存：

```text
arbitrary hex
random px spacing
random radius
random font-size
random line-height
one-off status colors
```

允许存在真正特殊的 media / canvas business values，但必须有业务理由。

---

## 6.4 Graphite Canvas Theme Mapping

Astryx neutral theme 只能作为起点。

必须映射到现有 Graphite Canvas，而不是直接使用默认外观。

当前 Graphite Canvas 已确定的视觉方向必须保留：

- dark neutral background；
- 非纯黑；
- 低对比冷灰 divider；
- restrained radius；
- 蓝 / 紫 / 绿 / 黄 / 红状态色；
- 紫色克制使用；
- Media Canvas 优先；
- UI chrome 不抢商品视觉内容。

F3.5 必须产出：

```text
CommerceCanvas semantic token
→ Astryx token / theme token
→ fallback / custom token
→ usage
```

# 7. F3.5-D — Typography Contract

Typography 是 F3.5 的 P0，不是装饰项。

必须建立固定层级。

至少定义：

| Role | 用途 |
|---|---|
| Page Title | 页面唯一一级标题 |
| Page Context | 页面标题旁的 run / job / product context |
| Section Title | 大区域标题 |
| Panel Title | Inspector / side panel / card header |
| Body | 正文 |
| Label | 字段名、表格标签 |
| Metadata | 次级数据 |
| Caption | 说明、辅助提示 |
| Metric | 关键数字 |
| Status | 任务状态 |
| Code | ID / hash / model / provider / route key |
| Timestamp | 时间信息 |

每个 role 必须固定：

```text
font family
font size
font weight
line height
letter spacing
color role
allowed usage
```

禁止新页面再随意添加：

```text
text-[11px]
text-[13px]
leading-[17px]
```

除非更新 typography contract 并说明理由。

---

CommerceCanvas 客户 UI 为中文。

Typography validation 必须覆盖：

- 中文标题；
- 中文长句；
- 中英混排；
- SKU；
- Model name；
- Provider；
- USD cost；
- percentage；
- timestamp；
- trace sequence；
- artifact ID；
- locale code。

不能只用英文 Astryx 示例验证。

# 8. F3.5-E — UI Density Contract

目标：

> 像成熟的生产工作台，而不是“每一块数据一个漂亮 Card”的 AI Demo。

## 8.1 默认优先级

对于高密度、可扫描数据：

```text
Row / List / Table
>
Panel
>
Card
```

Card 必须有明确 grouping 理由。

禁止：

```text
Card
  Card
    Badge
    Badge
```

成为默认布局方式。

---

## 8.2 建立固定 Density Levels

建议定义：

```text
compact
default
comfortable
```

CommerceCanvas 生产页面默认：

```text
compact / default
```

而不是 consumer-style comfortable。

必须统一：

- row height；
- control height；
- panel padding；
- horizontal gap；
- vertical rhythm；
- icon size；
- label / value spacing；
- table density；
- toolbar density。

---

## 8.3 Badge Policy

Badge 只用于真正需要快速扫描的离散状态。

不允许所有 metadata 都 Badge 化。

推荐：

```text
Status / Risk / Review / Route state
→ Badge

ID / Cost / Time / Count / Model
→ Text / Metadata / Code
```

# 12. Motion Contract

CommerceCanvas 是生产工具，不是营销网站。

Motion 应：

- 短；
- 克制；
- 有状态含义；
- 不阻碍操作；
- 不用大面积 spring animation 制造“高级感”。

重点统一：

```text
hover transition
popover/dialog enter/exit
progress change
skeleton/loading
selection/focus
trace/evidence reveal
```

Live Intelligence 的动态展示可保留产品特性，但必须与基础 motion token 协调。

# 15. Agent / ZCode UI 执行规则
